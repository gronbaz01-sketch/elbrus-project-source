# SEO — техническая база (Фаза 1)

Репозиторий: `elbrus-360-portal`. Все решения приняты автономно и зафиксированы здесь для проверки.

## Что сделано

1. **Инфраструктура meta-тегов** — `react-helmet-async` + компонент `src/components/seo/SEO.tsx`.
   Каждая публичная страница теперь рендерит `<SEO title=... description=... path=... jsonLd=... />`
   с уникальными title/description/canonical/OG/Twitter.
2. **Fallback-теги в `index.html`** — убраны placeholder'ы Lovable ("Lovable App"), проставлен `lang="ru"`,
   реальные title/description/OG для случаев, когда краулер не выполняет JS.
3. **JSON-LD**: `Organization` + `WebSite` на главной, `BreadcrumbList` на всех разделах (фабрики в `SEO.tsx`,
   легко добавить `LodgingBusiness`/`FAQPage`/`LocalBusiness`, когда появятся структурированные данные объектов).
4. **noindex** на `/admin`, `/auth`, `/404` — служебные страницы не должны попадать в индекс.
5. **robots.txt** — явный `Disallow: /admin`, `/auth`, ссылка на `sitemap.xml`.
6. **sitemap.xml** — статический, покрывает 5 текущих публичных маршрутов.
7. **Геофокус**: заголовок главной страницы правлен с «гид по Кабардино-Балкарии» на «гид по Приэльбрусью» —
   вся формулировка сайта теперь последовательно завязана на Приэльбрусье, а не на регион в целом.
8. Прогнан `tsc --noEmit` и `npm run build` — сборка проходит чисто.

## Важные ограничения, которые нужно решить осознанно (не решал сам за вас)

- **Домен-placeholder**: `SITE_URL = "https://elbrus360.ru"` в `SEO.tsx`, `robots.txt`, `sitemap.xml` — реальный
  production-домен неизвестен, нужно заменить одним поиском/заменой перед деплоем.
- **OG-изображение**: ссылка на `/og-default.jpg` — файла физически нет, нужно подготовить реальное
  изображение 1200×630.
- **Рендеринг остаётся client-side SPA**. Я не стал самостоятельно принимать решение о переезде на
  Next.js/Remix или добавлении prerender-шага — это архитектурное решение с последствиями для хостинга
  (проект сейчас живёт в экосистеме Lovable со статическим Vite-билдом). Meta-теги через `react-helmet-async`
  корректно видит Google (выполняет JS), но Яндекс и Bing индексируют JS заметно хуже — это системный риск
  для целей ТЗ (Яндекс явно упомянут как одна из целевых систем).
- **Soft-404**: SPA всегда отдаёт HTTP 200 с клиентским роутингом, включая несуществующие пути — это должно
  чиниться на уровне хостинга (rewrite + правильный статус), а не только через `noindex` в React.

## Фаза 3 — SEO Content Engine + программные страницы объектов (сделано в этом проходе)

1. **Миграция БД** (`supabase/migrations/20260920090000_seo_content_engine_fields.sql`): в `apartments`,
   `cafes`, `taxi_services` добавлены `slug` (уникальный, обязательный, для существующих записей
   заполнен значением `id`), `seo_title`, `seo_description`, `seo_h1`, `noindex`.
   **Не применена к реальной БД** — у меня нет доступа к вашему Supabase-проекту из этой песочницы.
   Нужно прогнать через Supabase CLI/Lovable Sync перед деплоем.
2. **Detail-страницы объектов**: `/apartments/:slug`, `/cafes/:slug`, `/taxi/:slug` — реализуют
   `SEO_PROGRAMMATIC_PAGES` из ТЗ. Каждая тянет данные по `slug`, использует `seo_title`/`seo_description`/
   `seo_h1`/`noindex` из БД с осмысленным фоллбэком, если админ их не заполнил. Есть `LodgingBusiness`/
   `Restaurant`/`Service` + `BreadcrumbList` JSON-LD, обработка "не найдено" (карточка не пропадает молча),
   перелинковка на остальные разделы и `/prielbrusye`.
3. **SEO Content Engine в `Admin.tsx`**: в каждую форму (жильё/кафе/такси) добавлен блок SEO — slug, SEO
   title, SEO description, H1, чекбокс noindex. Slug генерируется автоматически из названия
   (транслитерация в `src/lib/utils.ts`), если админ не ввёл свой; сохранение теперь проверяет ошибки

5. **Динамический sitemap объектов** — `supabase/functions/sitemap-objects/index.ts`, Edge Function,

   **Не задеплоена** — нужно `supabase functions deploy sitemap-objects`.

## Фаза 3.5 — решён блокер рендеринга (SSG поверх текущего стека, без миграции)

Реализован полноценный build-time prerendering по паттерну Vite SSR-guide — **проверено вживую в
песочнице**, а не только написано:

- `src/entry-client.tsx` / `src/entry-server.tsx` — клиентская и серверная точки входа; `App.tsx`
  больше не содержит `BrowserRouter` внутри себя (роутер теперь снаружи, разный для клиента/сервера).
- `scripts/prerender.mjs` — после `vite build` (клиент) и `vite build --ssr` (сервер) рендерит
  `/`, `/prielbrusye`, `/aktivnosti` в реальный HTML через `renderToString`, вытаскивает
  `react-helmet-async`-теги (title/description/OG/canonical/JSON-LD) и пишет готовые файлы
  `dist/index.html`, `dist/prielbrusye/index.html`, `dist/aktivnosti/index.html`.
- Проверено: `npm run build` собирает всё за один проход; поднял `vite preview` и curl'ом убедился,
  что `/prielbrusye/` отдаёт правильный `<title>` и полный HTML контента без единой строчки JS на
  стороне клиента (то, что нужно Яндексу и Bing).
- По пути нашёл и починил реальный баг: `src/integrations/supabase/client.ts` обращался к
  `localStorage` на уровне модуля — в Node (при сборке/SSR) это падает с `ReferenceError`.
  Обернул в `typeof window !== "undefined"`. **Важно**: этот файл помечен как
  "автоматически генерируется" — если Lovable пересоздаст его через Supabase-интеграцию, правку
  придётся перенести туда же заново.
- `src/entry-client.tsx` использует `hydrateRoot` для prerender-страниц и `createRoot` для остальных
  (`/apartments`, `/cafes`, `/taxi`, `/cameras`, `/auth`, `/admin` — они получают контент только на
  клиенте, так как зависят от Supabase, а сеть песочницы не имеет доступа к вашему реальному проекту,
  чтобы забрать данные на этапе сборки).
- Добавлен `public/_redirects` (формат Netlify/Cloudflare Pages) для SPA-фоллбэка.

### Осталось нерешённым по рендерингу (честно, а не замалчиваю)

- **Soft-404 не исправлен**: SPA всегда отдаёт HTTP 200, включая несуществующие пути. Настоящий
  404-статус требует правил на уровне хостинга — я не знаю точно, какой хостинг использует Lovable
  под капотом, поэтому не могу написать конкретный конфиг с уверенностью, что он сработает.
- Prerender сейчас покрывает только 3 маршрута без Supabase-данных. `/apartments/:slug` и подобные
  detail-страницы **не** prerender'ятся — сеть песочницы не может достучаться до вашего реального
  Supabase URL, чтобы забрать данные на этапе сборки. Как это закрыть на вашей стороне: в
  `scripts/prerender.mjs` добавить шаг, который до рендера запрашивает список активных
  apartments/cafes/taxi (через service-role ключ, не anon) и добавляет их пути в `PRERENDER_ROUTES` —
  инфраструктура (helmet, JSON-LD, SEO-компонент) уже готова, не хватает только доступа к данным
  в момент сборки.

## Фаза 4 — устойчивость к неприменённой миграции (можно заливать прямо сейчас)

Вы сказали, что не готовы самостоятельно применять миграцию БД / деплоить edge function — поэтому
переделал так, чтобы **это не блокировало деплой и обычную работу с сайтом**:

1. **Админка работает и без миграции.** Сохранение жилья/кафе/такси (`saveWithSchemaFallback` в
   `Admin.tsx`) сначала пробует сохранить вместе с SEO-полями; если БД отвечает "column does not
   exist" (миграция не применена), автоматически повторяет сохранение без них. Это значит: редактирование
   телефона, email, цены, описания и т.д. работает прямо сейчас, на текущей схеме БД, без каких-либо
   действий с вашей стороны. SEO-поля (slug/SEO title/description/H1/noindex) просто не будут сохраняться,
   пока миграция не применена — но ничего не сломается.
2. **Ссылки на detail-страницы не ломаются.** Списки жилья/кафе/такси используют `apt.slug ?? apt.id`
   — если колонки `slug` ещё нет, ссылка ведёт на `/apartments/<id>` вместо `/apartments/undefined`.
   Сами detail-страницы (`/apartments/:slug` и т.д.) до применения миграции будут показывать
   аккуратную страницу "не найдено" вместо белого экрана/краша — это уже было предусмотрено раньше.
3. **Домен подхватывается автоматически.** `SITE_URL` в `SEO.tsx` теперь берётся из
   `window.location.origin` в браузере — на какой бы хостинг вы ни залили сайт (Netlify, Vercel,
   Lovable, что угодно), canonical/OG-теги на клиентских страницах будут указывать на правильный
   реальный адрес без какой-либо ручной правки. Единственное исключение — 3 prerender-страницы
   (`/`, `/prielbrusye`, `/aktivnosti`), у них при сборке ещё не известен адрес браузера, поэтому в них
   останется технический плейсхолдер `elbrus360.ru` в `<link rel="canonical">`, пока вы (когда будет
   удобно) не поменяете одну строку в `SEO.tsx`. Это не мешает сайту работать и открываться.
4. Убрал из `robots.txt` ссылку на sitemap-edge-function, пока она не задеплоена — чтобы ничего
   не указывало в никуда. Функция (`supabase/functions/sitemap-objects`) осталась в проекте на
   будущее, просто не подключена.

**Итог: можно заливать на любой статический хостинг прямо сейчас.** Базовая функциональность (все
страницы, редактирование телефонов/email/цен/описаний в админке) работает независимо от того, применена
миграция или нет. SEO Content Engine (slug-страницы объектов, кастомные SEO title/description) заработает
сам собой, как только миграция будет применена — специально ничего включать не нужно.
